# 我用 Spring Boot + Vue 3 做了个儿童英语启蒙 APP，吉祥物是一只戴黄围巾的灰老鼠

> 作为一个经常被亲戚追问"能不能给孩子做个学英语的 App"的开发者，我决定不再只回答"用某某 App 就行"。于是我用下班时间做了 **Mimi 启蒙乐园**——一个面向 4–6 岁儿童的开源启蒙学习平台。本文聊聊它的产品设计、技术选型和一些"踩过才懂"的工程决策。

## 一、为什么要自己造一个

市面上儿童英语 App 不少，但在我陪家里小朋友使用的过程中，有几个痛点始终绕不开：

- **广告和付费墙太多**：孩子学到一半弹窗，体验割裂；
- **课程内容不可控**：无法针对自家孩子的薄弱点补充内容；
- **发音评测基本是黑盒**：不知道分数怎么打的，更无法本地化部署；
- **开源、可二开的选项几乎没有**：家长想自托管、幼儿园想定制主题，都无从下手。

所以我给自己的目标是：**开源、可自部署、发音评测可解释、内容可扩展、单 JAR 就能跑起来**。

最终成品叫 **Mimi 启蒙乐园**，在线 Demo：http://39.96.59.120:8080/app/

仓库地址：https://github.com/pengguogo/english-app

## 二、产品长什么样

一句话概括：**每天 15 分钟，陪孩子快乐成长**。

支持英语自然拼读、跟读评分、数学练习、语文阅读和学习进度管理。游戏化课程地图让孩子主动学完一课又一课。

### 七种课型覆盖一个完整的启蒙闭环

| 类型 | 说明 | 交互模式 |
|------|------|----------|
| WORD | 看图认字 | 听发音 → 跟读评分 |
| SENTENCE | 句型朗诵 | 听音 → 跟读评分 |
| READING | 图文阅读 | 翻页阅读 |
| QUIZ | 选择题 | 判对错，答错自动入错题本 |
| CALCULATE | 计算题 | 数字输入判对错 |
| PHONICS | 自然拼读 | 字母发音规则学习 |
| DIALOGUE | 情景对话 | 角色扮演式对话练习 |

### 三个让人坚持做下去的小设计

1. **错题本 + 已学回顾**：答错自动入册，按掌握度筛选复习，统计累计星星与均分；
2. **游戏化课程地图**：按主题 / 单元组织，星级奖励与解锁式进度；
3. **吉祥物 Mimi 只在三处出现**：欢迎、学习陪伴、完成庆祝。不打扰学习节奏，这一点我觉得比很多"全程贴脸卖萌"的产品更克制。

> 吉祥物 Mimi 是一只戴黄围巾的灰老鼠，资产放在 `frontend/src/assets/mascot/`。为什么是老鼠？因为孩子对"小动物闯关"的接受度远高于"老师讲课"。

## 三、技术选型：为什么是这套

先放结论，技术栈如下：

| 层级 | 技术 |
|------|------|
| 后端 | Java 17 · Spring Boot 3.2 · JPA · Flyway · SQLite |
| 前端 | Vue 3 · Vite · Pinia · Vue Router |
| 语音 | 百度 TTS + ASR（适配器模式，可切供应商） |
| 部署 | 单 JAR（Vue 构建嵌入 Spring Boot static/）· GitHub Actions 自动部署 |

### 1. 为什么用 SQLite 而不是 MySQL

一个面向家庭场景的启蒙应用，数据量级并不大，**单文件 SQLite 把部署门槛降到了最低**：一台 2C2G 的阿里云小机器，装个 JRE 就能跑。配合 Flyway 管理 schema 迁移，开发和运维都轻得很。

当然代价是写并发有限，但对一个"固定单用户、无登录系统"的启蒙场景来说，这个 trade-off 是划算的。

### 2. 为什么是"单 JAR 部署"

这是我个人最满意的一个工程决策。Vue 构建产物不另起 Nginx，而是**直接写入 `backend/src/main/resources/static/app/`**，最终打成一个 JAR：

```bash
cd backend && mvn test                       # 1. 后端测试
cd ../frontend && npm ci && npm run build    # 2. 构建前端（写入后端 static/app/）
cd ../backend && mvn clean package           # 3. 打包
java -jar target/english-app-backend-*.jar   # 4. 启动，访问 http://localhost:8080/app/
```

好处很明显：

- **部署只有一个产物**：`scp` 一个 JAR 上去就完事；
- **没有跨域问题**：前后端同源；
- **CI 简单**：GitHub Actions 一条流水线搞定构建 + 部署；
- **资源占用低**：省掉了 Docker daemon 的内存开销，2C2G 机器毫无压力。

> 一行 Docker 也能跑：`docker compose up`，然后访问 `http://localhost:8080/app/`。

### 3. 发音评分：浏览器录音 + TTS + ASR 相似度

这是儿童英语 App 的"灵魂功能"。Mimi 的做法是：

- **采集**：Web Audio API 在浏览器端录音，无需安装客户端；
- **合成**：百度 TTS 下发标准发音；
- **评分**：孩子跟读后上传音频，走 ASR 转写，再与目标文本做相似度评分。

关键工程约束我写在了 AGENTS.md 里：**AI 功能必须设超时 + 降级 + 结果校验**。也就是说，语音接口挂了不能让整个课程崩掉，而是返回降级提示，其余功能正常。这一点对面向孩子的产品尤其重要——孩子对"突然白屏"的容忍度是零。

语音供应商走的是适配器模式，后续可以平滑切到其他厂商，不污染业务层。

### 4. 课程内容的"工程化"交付

这是很多做教育产品的开发者容易忽略的点：**课程内容也是代码资产**，不能随手改数据库。

Mimi 的做法是：

- 所有课程新增 / 修改**必须通过新的 Flyway 迁移交付**，禁止修改已提交的迁移；
- **每个可视学习项必须配图**，`image` 不得为空，emoji 不能替代图片；
- 图片文件、课程迁移和素材来源记录必须**同批提交**；
- 合并前必须验证图片 URL 和课程页面。

> 这套规则写在 `docs/project-build-rules.md` 里，本质上是给"内容生产"也加了一道 CI 门禁。教育产品的内容质量比代码质量更影响口碑，这一步不能省。

## 四、几个值得一提的"小而美"实现

### 1. 设计令牌统一管理，禁止硬编码色值

前端所有颜色都走 `frontend/src/styles/tokens.css` 里的 CSS 变量：

```css
var(--xxx)
```

好处不只是"主题切换方便"，更重要的是**让 AI 辅助生成代码时也能遵守视觉一致性**——AGENTS.md 里明确写了 `禁止硬编码色值`，这条规则对人和对 AI 都有效。

### 2. 动效只用 CSS，不引入动画库

儿童产品很容易陷入"动效越多越好"的陷阱。Mimi 的约定是：动效只用 CSS `transition` / `keyframes`，且装饰性动画必须包裹：

```css
@media (prefers-reduced-motion: no-preference) { ... }
```

即尊重"减少动效"的系统偏好。这对有前庭功能敏感的孩子是实打实的友好。

### 3. 分层严谨的后端架构

后端严格分层，且对 AI 生成代码也做了强约束：

- 分层：`domain` / `repository` / `service`（+ `Impl`）/ `controller` / `dto` / `exception` / `config`；
- **构造器注入，禁用 `@Autowired` 字段注入**；
- Controller 不返回 JPA 实体，统一用 `XxxRequestDTO` / `XxxResponseDTO`；
- 统一响应：`{code, message, data}`；
- 全局异常：`@RestControllerAdvice`，业务异常继承 `RuntimeException`，异常码用枚举；
- 日志：SLF4J，`log.error("描述", e)`，禁用 `printStackTrace`。

> 这些规则之所以值得拿出来说，是因为**它们既是人写的规范，也是 AI 编码助手的 system prompt 的一部分**。项目里的 `AGENTS.md` 把这些约定喂给 AI，让生成的代码直接符合团队规范，省去了大量 review 成本。

### 4. 测试先行

Service 公共方法必须有单测，类名 `XxxTest`，方法 `should_期望行为_当_条件`，JUnit 5 + Mockito，AAA 模式。

正式交付顺序被钉死在 AGENTS.md 里：

> 后端测试 → `npm ci` → 前端构建 → Maven 完整打包；完成前不得用 `-DskipTests` 代替验收。

这一条是防止"为了快上线跳测试"的自我约束，也是防止 AI 助手自作主张跳过测试的护栏。

## 五、关于"AI 协作开发"的一点心得

这个项目从第一行代码起，就是在 AI 编码助手的深度参与下推进的。我把所有工程约定写进了 `AGENTS.md`，它既是团队协作文档，也是 AI 的 system prompt。

几个体会：

1. **约定要写成可执行、可校验的**：比如"禁止硬编码色值""不得用 `-DskipTests` 代替验收"——AI 会照做，人也会照做。
2. **分层和命名约定是 AI 的护栏**：明确"构造器注入""Controller 不返回实体"，AI 生成的代码天然符合规范，review 成本骤降。
3. **内容生产也要工程化**：课程配图、Flyway 迁移、素材来源记录同批提交，本质是给"非代码资产"也上 CI。

如果你也在用 AI 助手做项目，强烈建议把 `AGENTS.md` 认真写一遍——它比任何 prompt 技巧都管用。

## 写在最后

做儿童产品，最大的挑战不是技术，而是**克制**——克制广告、克制弹窗、克制"全程贴脸卖萌"的吉祥物、克制"为了快上线跳测试"的冲动。

Mimi 启蒙乐园想做的，就是把这些"克制"工程化：用 AGENTS.md 约束 AI，用 Flyway 约束内容，用单 JAR 约束部署复杂度，用 CSS 变量约束视觉一致性。

如果这个项目对你有启发——无论是作为家长、作为开发者，还是作为"想用 AI 协作做产品"的人——欢迎来仓库点个 ⭐，也欢迎来 Issue 区聊聊你的想法。

孩子的时间很宝贵，我们做的每一行代码，最终都会变成他们每天 15 分钟里的体验。值得认真对待。
